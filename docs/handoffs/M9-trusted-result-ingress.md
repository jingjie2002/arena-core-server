# M9 非技术交接：可信比赛结果接入

## 现在增加了什么

竞域现在不再自己假装打完一场比赛并编造胜负。两名玩家匹配、进房并准备好以后，房间会等待真正负责战斗判定的模块告诉它“谁赢、谁输”。收到可信结果后，竞域才负责可靠结算、修改积分、更新排行榜并通知玩家。

可以把职责理解成：

1. 游戏客户端负责连接、匹配、进房和准备。
2. 战斗服负责真正的战斗和胜负判定。
3. 竞域负责等待结果、检查结果属于这场比赛、只结算一次、保存事实并通知玩家。

本项目暂时没有真正的战斗服，因此自动测试使用 `DemoBattleAdapter` 模拟它。这个模拟器走的也是正式可信入口，没有直接修改服务器内部数据。

## 一场比赛现在怎样完成

```text
两名玩家连接并匹配
        ↓
两人进入同一房间并 Ready
        ↓
房间进入 AwaitingResult（等待比赛结果）
        ↓
战斗服 / DemoBattleAdapter 提交胜负
        ↓
竞域检查身份、房间、玩家和规则版本
        ↓
MySQL 事务结算成功
        ↓
双方收到结果，排行榜更新或进入可恢复状态
```

如果战斗服重复发送完全相同的结果，竞域会返回上次已经保存的结算，不会重复加分；如果同一场比赛被发送了不同胜负，竞域会拒绝。一直没有结果则超时结束，并且不会修改任何人的积分。

## 将来怎样接入真实游戏

真实战斗服只需在比赛结束后调用：

`POST /internal/v1/match-results`

请求要携带服务间 Bearer token，并提供 result、match、room、胜者、败者、规则版本和完成时间。这个端口默认关闭、默认只接受本机连接；凭证从环境变量读取，不写进仓库或页面。

普通玩家不能调用这个写入口。玩家协议只能收到 `MatchResultCommitted`，或者断线回来后用 `GetMatchResult` 查询自己参与比赛的结果。

## M9 已自动证明的内容

- 没有 token 或 token 错误时不能提交结果。
- 合法结果能完成真实 TCP → 房间 → HTTP 结果入口 → MySQL 结算 → 玩家通知闭环。
- 相同结果不会重复加分，不同结果会冲突。
- 服务重启后仍能从 MySQL 查询已经提交的结果。
- 结果等待超时不会产生结算。
- GCC、Clang、真实 MySQL 和 Redis 都已经通过自动验证。

## 这一步还没有做什么

M9 只完成后台真实接入边界。它没有制作可调参数的 Lab 控制台，没有接入 Toxiproxy 故障代理，也没有把页面改造成最终 QA 实验台；这些属于后续 M10/M11。当前不需要你手动测试或理解代码。
