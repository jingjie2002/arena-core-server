# ADR-0001：采用 C++17 模块化单体

- 状态：Accepted
- 日期：2026-08-11

## 背景

项目需要在有限时间内完整展示网络并发、匹配、房间、结算、缓存和可观测性。拆成微服务会增加部署、RPC 和跨服务一致性成本，却不能提高 v1 的核心证明力。Go CoreRank 可提供业务参考，但其 Redis 事实源和服务拆分不能直接等同于目标设计。

## 决策

使用一个 C++17 服务进程，内部按 `net/session/match/room/settlement/rank/observer` 模块划分。模块通过明确接口、值对象和事件协作，构建系统允许未来拆分，但 v1 不引入内部网络 RPC。

CoreRank 只复用业务概念和失败经验，不逐行翻译、不修改其仓库。

## 后果

- 优点：一条命令可运行，端到端调试和 fresh-clone 更可控；事务边界清晰；简历叙事集中。
- 代价：进程级故障影响全部模块；需要严格线程所有权避免“单体等于共享状态”。
- 缓解：模块接口、strand 所有权、持久化事实源和独立测试共同限制耦合。

## 未采用方案

- 微服务：v1 运维成本高，超出已锁定范围。
- 复制 Go CoreRank 架构：保留了本项目要主动修复的双写与事实源问题。
- 单线程事件循环：实现简单，但无法展示阻塞存储隔离及并发设计。
