## 背景与范围

- 背景说明：用户认为 v1.0.1 页面更像教学演示，无法说明它是不是可被实际接入的游戏服务端模块，并要求重新设计项目目标、功能和控制台，同时参考 GitHub 优秀项目并适配现有技术栈。
- 本轮目标：基于真实需求定义项目定位、使用者、功能边界、P0/P1、不做项、技术架构、验收条件和实施阶段。
- 本轮边界：只做设计和公开资料调研；不修改业务代码、不启动新版本开发、不合并 `main`、不上传 GitHub。

## 实现方案与取舍

- 方案概述：将项目定位为“C++17 1v1 竞技游戏对局编排与结算服务”，并把玩家 TCP、可信结果入口、只读 Observer 和本地 Lab Controller 分成四个权限边界。
- 关键取舍一：v1.1 不再由 Room 在 Ready 后内部自动生成胜负，而是进入 `AwaitingResult`；本地 Demo Battle Adapter 和未来战斗服通过同一个可信结果 API 提交。
- 关键取舍二：Web 被定义为开发/QA 控制台，不是玩家界面；参数化 Run 必须走真实 Robot、结果适配器和依赖代理，不能直接写数据库或业务内存。
- 关键取舍三：继续使用 C++17、Boost.Asio/Beast、Protobuf、MySQL、Redis、Lua、CMake 和原生 Web；不迁移到 Go/Kubernetes、MMO 框架、C++20/23 或大型前端框架。
- 关键取舍四：v1.1 只锁五个 P0 场景；MySQL 故障页面化、Run 对比和更多压力 UI 留作 v1.2 候选，防止范围再次膨胀。
- 新依赖建议：只在可选 `lab` Compose profile 中加入固定版本 Toxiproxy，用于真实 Redis 网络故障；正式 profile 不启动它。

## GitHub 参考证据

- Open Match：借鉴 Ticket/Profile/Assignment 的职责分离，不采用 Go/Kubernetes 分布式部署。
- Nakama：借鉴游戏能力边界、权威比赛和开发控制台分离，不采用账号/社交/聊天/商城等平台功能。
- Moon：借鉴 Service 所有权与消息边界，不进行 C++23/Lua 协程框架重写。
- BoostServerTech Chat：借鉴 C++/Boost/MySQL/Redis/Compose/文档的一体化交付，不采用 C++20 和 Next.js。
- CppServer：借鉴显式生命周期、示例和性能证据，不替换当前 Boost.Asio 实现。
- Toxiproxy：借鉴确定性 TCP 故障代理和清理 API。
- k6：借鉴场景、阶段、阈值和结果输出模型，不新增 JavaScript 测试主线。
- KBEngine：借鉴底层与游戏逻辑分层及客户端接入意识，不扩张为 MMO 引擎。
- Boost.Asio：继续以官方模块的示例/测试思路维护当前 callback + strand 路线。
