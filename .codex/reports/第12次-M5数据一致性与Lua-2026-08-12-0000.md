## 背景与范围

- 背景说明：M4 已能生成冻结的确定性房间结果，但仍由内存占位结算，排行榜与持久化一致性尚未建立。
- 本轮目标：建立 MySQL 事实事务、Redis 派生缓存、dirty 修复、Lua 规则和 Room 异步结算闭环。
- 本轮边界：不实现 M6 观察台，不做 M7 压力/Sanitizer，不提前制作 M8 Compose 或公开发布。

## 实现方案与取舍

- 方案概述：Room 将冻结结果交给 SettlementGateway；有界 StorageExecutor 执行 MySQL 事务，提交后更新 Redis。缓存失败保留事务内 dirty，由后台重放或全量重建。
- 关键取舍：MySQL 是唯一事实源，Redis 永远不参与事实事务；相同指纹幂等、不同指纹冲突；排行并列以 player id 稳定打破。
- 适配取舍：用 Ubuntu 可直接安装的 MySQL Connector/C++、hiredis 和 Lua C API 薄层替代原计划中的更高层封装，降低 fresh-clone 依赖风险；见 ADR 0004。
- 安全边界：Lua 不开放标准库，并设置 10000 指令粒度的执行预算；配置只保存密码环境变量名，不保存密码。

## 实际发现与修复

- 问题：`TIMESTAMP` 字段配合 `UTC_TIMESTAMP()` 在 `+08:00` 会话下让新 dirty 记录看起来位于未来。
- 修复：写入和扫描统一使用 `CURRENT_TIMESTAMP(6)` 的会话时区语义；真实故障—恢复测试随后通过。
- 并发补强：Redis 写入/重建增加串行互斥；dirty 清理采用条件删除，避免重建与新提交竞态误删。

## 风险与回滚点

- 已知风险：MySQL 目前按任务创建连接，没有单独连接池；并发受到有界 StorageExecutor 控制。Redis 已有小型连接池。
- 影响范围：结算、排行榜、Room 关闭条件、服务端启动配置、构建依赖和 CI。
- 回滚策略：M5 边界通过 SettlementGateway/RankCache/Repository 接口隔离；可切回内存 gateway 做无数据依赖测试，但不能把它作为生产完成状态。
