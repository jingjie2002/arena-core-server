# Scope Lock Rules

## 目标

在保证开发推进效率的前提下，防止任务越界、顺手扩写和高风险误操作。

## 默认范围策略（中等强度）

- 只处理当前用户明确要求的目标。
- 允许同模块内为完成当前目标所需的小幅修复。
- 不允许跨模块功能扩展、架构升级或产品方向改写。

## `.codex` 管理区边界

- `.codex/` 默认只承载 AI 协作管理材料：状态、方案、项目地图、规则、模板、报告。
- 不把正式项目资料、需求文档、业务文档、任务清单、源码或交付物直接放入 `.codex/`，除非用户明确要求。
- 新增 `.codex/` 文件前，必须先判断它是否属于管理记录；如果是正式资料，应放到 `.codex/` 外的业务目录。
- 对已经误放入 `.codex/` 的正式资料，可以在说明原因后迁出；迁出后在状态或报告中保留路径引用即可。

## 开工前最小确认

除极小文案修改外，默认先确认以下 4 点：

1. 本轮只做什么。
2. 本轮明确不做什么。
3. 预计改哪些文件或模块。
4. 本轮准备如何验证。

## 允许的范围内扩展

满足以下条件时，可不额外确认直接处理：

- 与当前改动直接耦合的编译错误或类型错误。
- 为当前改动补充最小必要测试。
- 与当前改动直接相关的注释、说明和状态记录更新。

## 必须先确认的情况

出现下列任一情况时，先停下来说明，再继续：

- 删除业务代码、配置、测试、文档、数据文件。
- 跨目录批量替换。
- 目录重组或大规模重命名。
- 新增依赖或升级依赖。
- 修改数据库结构或迁移脚本。
- 修改对外接口契约（API、消息协议、数据格式约定）。
- 大规模自动生成文件（超过 20 个）。

## 说明格式

需要先确认时，尽量用简短中文说明：

1. 准备做什么
2. 为什么想这样做
3. 可能影响哪里
4. 如果这次不做，会留下什么

## 范围失配处理

- 如果执行中发现需求边界与现状冲突，应先暂停扩展实现，先反馈边界冲突和可选处理路径。
- 如果发现与本轮无关的潜在问题，仅记录到报告中的“遗留问题/建议”，不擅自展开处理。

## 报告要求

- 报告必须写清“本轮改动”和“本轮未做项”。
- 若有高风险动作，必须单独写出动作原因、影响范围和回滚思路。
