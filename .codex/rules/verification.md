# Verification Rules

## 目标

将“已完成/已修复/可运行”建立在可复核的验证证据上，适配跨技术栈项目。

## 通用验证基线（按改动触发）

仅对“本轮改动涉及的技术栈”执行验证，不要求每轮全量跑所有栈。

默认基线：

1. 语法或静态检查（若该栈存在对应工具）。
2. 构建或编译检查。
3. 关键单元测试（若项目已有测试且与改动相关）。

## 跨栈示例（示例不是强绑定命令）

- Go：`go vet ./...` + `go test ./...`
- Node/TypeScript：`npm run lint`（若有）+ `npm run build` + 相关测试命令
- Python：静态检查工具（如 ruff/mypy，若有）+ 相关测试命令
- Java：构建命令 + 相关测试命令
- .NET：构建命令 + 相关测试命令
- 桌面端或打包链路改动：补充对应打包或构建验证

## 通过标准

- 能全量验证时：按本轮改动完成相关验证并记录结果。
- 无法全量验证时：允许部分验证，但必须写明：
	1. 未验证项
	2. 原因
	3. 影响范围
	4. 补偿计划

## 结论表达要求

不要只写“测试通过”。

应明确写清：
- 验证了什么
- 如何验证
- 结果是什么
- 当前是否可进入验收
- 仍未覆盖的边界

## 禁止事项

- 未验证即宣称完成
- 用无关验证替代本轮验证
- 隐去失败信息或未验证项
