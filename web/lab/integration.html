接入 A

游戏客户端

正式协议是长度帧包裹的 Protobuf Envelope。下面是职责顺序，不是可以直接复制运行的固定比赛数据。

客户端状态顺序

Hello / Resume
首次连接建立身份；短暂断线时使用轮换后的恢复凭证重新绑定 Session。
Heartbeat
在服务端超时窗口内维持连接活跃，不承载游戏战斗状态。
Queue / Cancel
提交匹配请求或离开队列。相同请求 ID 的重试必须得到一致结果。
Join / Ready
收到 MatchFound 后，携带加入凭证进入指定 Room；双方准备后等待外部比赛结果。
Result Read
接收 MatchResultCommitted，或通过 GetMatchResult 查询自己参与过的比赛。

客户端不能做什么

玩家协议没有“提交胜负”的消息。客户端不能修改他人积分、直接操作排行榜，也不能绕过房间状态创建结算。
  • 不要把服务凭证打包进游戏客户端。
  • 不要用 Observer 或 Lab API 代替玩家协议。
  • 收到断线或超时时，按稳定错误码处理并保留请求幂等键。

接入 B

可信战斗模块

结果入口默认关闭，只应在同机或私有网络启用。凭证来自运行环境，不能写进页面或日志。

提交接口

POST /internal/v1/match-results Authorization: Bearer <service-token> Content-Type: application/json { "result_id": "<全局幂等键>", "match_id": "<已存在比赛>", "room_id": "<对应房间>", "winner_id": "<胜者>", "loser_id": "<败者>", "rule_version": "<已加载规则版本>", "finished_at": "<UTC 时间>" }

调用方必须保证

  • result_id 全局唯一；网络重试必须复用同一个键和完全相同的内容。
  • 双方成员必须与 Room roster 完全一致，胜者和败者都在其中。
  • 只有战斗确实结束后才能提交，并提供 UTC 完成时间。
  • 冲突响应不能改换 result_id 强行重试，应作为一致性问题告警。
  • 查询只用于确认已提交事实，不会重新触发积分变更。
